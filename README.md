# BananaKart Backend Chronicles

## Episode 5: Database Starts Crying

As BananaKart grows, the number of orders grows with it.

Returning every order in one request and scanning large tables eventually becomes inefficient.

This episode focuses on:

* Pagination
* Query parameter validation
* Database indexes
* PostgreSQL `EXPLAIN`

* Order history endpoint

## Order History Endpoint

```http
GET /orders
```

Example:

```http
GET /orders?limit=20&offset=0
```

Only orders belonging to the authenticated user are returned.

```text
Authenticated user
        ↓
GET /orders
        ↓
current_user.id
        ↓
Find user's orders
        ↓
ORDER BY created_at DESC
        ↓
LIMIT + OFFSET
        ↓
Return order history
```

The user ID comes from JWT authentication rather than client input.

## Pagination

Returning every order becomes expensive as the amount of data grows.

Pagination limits how much data is returned in one request.

```text
limit
→ number of rows to return

offset
→ number of rows to skip
```

Example:

```http
GET /orders?limit=20&offset=0
```

```text
skip 0
return 20
```

Next page:

```http
GET /orders?limit=20&offset=20
```

```text
skip 20
return next 20
```

Memory:

```text
limit  → how many?
offset → where to start?
```

---

## Query Validation

Pagination parameters are validated before the endpoint logic runs.

```python
limit: int = Query(default=20, ge=1, le=100)
offset: int = Query(default=0, ge=0)
```

This prevents requests such as:

```http
GET /orders?limit=1000000
```

or:

```http
GET /orders?limit=-5
```

Invalid values return:

```text
422 Unprocessable Entity
```

## Order History Query

The SQL generated by the endpoint is conceptually:

```sql
SELECT *
FROM orders
WHERE user_id = ?
ORDER BY created_at DESC
LIMIT 20
OFFSET 0;
```

The important query pattern is:

```text
WHERE user_id = ?
ORDER BY created_at DESC
```

## Composite Index

A composite index was added for the order-history access pattern:

```text
(user_id, created_at)
```

SQLAlchemy:

```python
Index(
    "ix_orders_user_created_at",
    "user_id",
    "created_at",
)
```

The database change was applied through an Alembic migration.

The index matches the query because the query:

```text
filters by user_id
        ↓
orders by created_at
```

Memory:

```text
Indexes should match real query patterns.
```

---

## Leftmost Prefix Rule

The orders table already contained the idempotency index:

```text
(user_id, idempotency_key)
```

PostgreSQL was able to use that index for:

```sql
WHERE user_id = 1
```

because `user_id` is the leftmost column.

```text
Index: (A, B)

Useful:
A
A + B

Usually not useful:
B alone
```

## EXPLAIN

PostgreSQL `EXPLAIN` was used to inspect how the database planned to execute the order-history query.

```sql
EXPLAIN
SELECT *
FROM orders
WHERE user_id = 1
ORDER BY created_at DESC
LIMIT 20 OFFSET 0;
```

`EXPLAIN` helps answer questions such as:

```text
Is PostgreSQL scanning the table?

Is an index being used?

Is PostgreSQL performing a separate sort?
```

---

## Sequential Scan

The development database contains very little data.

For the small table, PostgreSQL chose:

```text
Seq Scan
        ↓
Filter by user_id
        ↓
Sort by created_at
        ↓
Limit
```

This is expected.

For a tiny table, scanning all rows can be cheaper than using an index.

```text
Index exists
≠
PostgreSQL must use it
```

The PostgreSQL query planner chooses the execution plan it estimates to be cheapest.

---

## Index Scan Experiment

For comparison, sequential scans were temporarily disabled:

```sql
SET enable_seqscan = off;
```

The query plan became:

```text
Index Scan Backward
using ix_orders_user_created_at
```

The separate sorting step disappeared.

Because the query requests:

```sql
ORDER BY created_at DESC
```

PostgreSQL can walk the B-tree index backwards.

Sequential scans were then restored:

```sql
SET enable_seqscan = on;
```

Disabling sequential scans was only a learning experiment and is not part of the application configuration.

## Key Takeaways

```text
Pagination
→ prevents unlimited responses

Index
→ helps PostgreSQL find and order rows efficiently

Composite index
→ matches multiple parts of a query pattern

EXPLAIN
→ shows the database query plan

Seq Scan

Index exists

```

## What Episode 5 Does Not Solve

Offset pagination works well for this project, but very large offsets can become inefficient.

```text
OFFSET 10
→ cheap

OFFSET 1,000,000
→ database may still need to skip many rows
```

Large-scale APIs often use cursor or keyset pagination instead.

That optimization is intentionally left out of the implementation.
